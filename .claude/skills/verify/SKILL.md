# 변경분 검증

검증 대상: $ARGUMENTS

- 위 검증 대상이 비어 있으면 `git diff upstream/main...HEAD` 를 대상으로 삼는다.
- 검증 대상이 patch 파일이면 `git apply --stat <파일>` 로 목록을 뽑고 patch 본문을 diff 로 읽는다.
- 절차와 역할 분리의 원칙은 저장소 루트의 `templates/verification-loop.md` 를 따른다. 이 Skill 은 그 문서의 **리뷰 세션** 역할만 한다.

## 1. 요청 범위 확인

- 이 변경으로 무엇을 요청했는지 한 문장으로 확인한다(사용자 메시지, PR 설명, 커밋 메시지).
- 요청 범위가 주어지지 않았으면 **판정하지 말고 먼저 사용자에게 묻는다.** 묻고 나서 답을 받기 전까지 2단계 이후로 넘어가지 않는다.

## 2. 변경 파일 목록과 diff 읽기

- `git diff --stat <대상>` 으로 변경 파일 목록을 먼저 본다.
- 파일마다 `git diff <대상> -- <파일>` 로 diff 를 읽는다. 판단에 문맥이 필요하면 해당 파일의 앞뒤 줄을 Read 로 확인한다.
- 변경 파일을 폴더별(`modern/api` · `modern/web` · `characterization` · `legacy` · `db` · 그 밖)로 묶어 둔다. 4단계에서 실행할 테스트를 이 묶음으로 정한다.

## 3. 체크리스트 대조

- 저장소 루트의 `templates/approval-checklist.md` 를 읽는다. 항목을 이 Skill 에 옮겨 적지 말고 그 파일을 기준으로 삼는다.
- 항목마다 **충족 · 미충족 · 확인 필요** 중 하나로 표시한다.
- 심각도(치명 / 경고 / 제안)는 그 파일의 "심각도 정의"를 따른다.
- 컨벤션 항목은 저장소 루트의 `CLAUDE.md` 의 코딩 컨벤션 · 금지 사항과 대조한다. `convention-check` Skill 을 쓸 수 있으면 그 결과를 근거로 쓴다.

## 4. 테스트 실행

변경된 폴더의 테스트만 실행한다.

| 변경된 폴더 | 명령 |
|---|---|
| `modern/api` | `cd modern/api && ./gradlew test` |
| `modern/web` | `cd modern/web && npm test` |
| 이관 코드(레거시 동작을 `modern/` 으로 옮긴 변경) | `cd characterization && npm test` (레거시 대상)<br>`cd characterization && TARGET_BASE_URL=http://localhost:8080 npm test` (새 API 대상) |

- **사용량 절약:** 전체 로그를 대화에 싣지 않는다. 출력은 파일로 돌리고(예: `> /tmp/verify-api.log 2>&1`), 거기서 **통과 · 실패 수와 실패한 테스트 이름만** 뽑아 남긴다.
  - `./gradlew test`: `modern/api/build/test-results/test/*.xml` 의 `tests` · `failures` · `errors` 속성과 실패한 `testcase` 이름
  - `npm test`(vitest): 로그 끝의 `Tests` · `Test Files` 요약 줄과 `FAIL` 로 시작하는 줄
- 실패한 테스트의 원인을 볼 때는 그 테스트 한 건의 실패 메시지 몇 줄만 인용한다.
- characterization 은 대상 서버가 떠 있어야 돈다. 레거시 서버(8081~8083)나 새 API(8080), MariaDB 가 꺼져 있어 실행하지 못했으면 "실행 못 함"과 그 이유를 적고, 사람에게 기동을 요청한다. 이때 "테스트 통과"는 충족으로 표시하지 않는다.

## 5. 승인 기준 판정

- 네 기준 **테스트 통과 / 치명 이슈 0건 / 요청 범위 이탈 없음 / 컨벤션 준수** 를 하나씩 판정한다.
- 네 기준이 모두 충족이면 승인, 하나라도 미충족이면 반려다.
- 요청 범위를 확인하지 못했으면 "요청 범위 이탈 없음"을 충족으로 표시하지 않는다.
- 이슈가 0건이면 경고 · 제안 수준까지 diff 를 한 번 더 본 뒤 판정한다.

## 출력 형식 (순서 고정)

```
판정: 승인 | 반려

| 기준 | 결과 | 근거 |
|---|---|---|
| 테스트 통과 | 충족 / 미충족 | 실행 명령과 통과 · 실패 수, 실패한 테스트 이름 |
| 치명 이슈 0건 | 충족 / 미충족 | 치명 이슈 번호 |
| 요청 범위 이탈 없음 | 충족 / 미충족 | 요청 문장 vs 변경 파일 목록 |
| 컨벤션 준수 | 충족 / 미충족 | 위반 이슈 번호 |

이슈 목록
| # | 심각도 | 파일:줄번호 | 근거 | 수정 방향 |
|---|---|---|---|---|
| 1 | 치명 / 경고 / 제안 | `경로:줄` | 어떤 규칙 · 어떤 위험인지 | 어떻게 고치면 되는지 |

확인 필요
- 파일:줄번호(알 수 있으면) — 판정하지 못한 이유
```

- 이슈 한 건은 심각도 · 파일:줄번호 · 근거 · 수정 방향을 모두 채운다.
- 이슈가 없으면 표 대신 "이슈 없음"이라고 적는다.

## 하지 말 것

- 코드를 수정하지 않는다. 판정과 수정 방향만 보고한다.
- 근거 줄번호를 댈 수 없는 지적은 이슈로 올리지 않고 "확인 필요"로 남긴다.
- 테스트를 실행하지 않고 통과했다고 쓰지 않는다.
- 전체 테스트 로그를 대화에 붙이지 않는다.
